# Decision Log

Append entries oldest first using: `date · decision · why · rejected alternative`.

- 2026-08-30 · Keep the current phase to product planning and low-fidelity wireframes only · The user explicitly requested planning before implementation · Rejected beginning framework selection or application scaffolding.
- 2026-08-30 · Treat recipes as reviewed, versioned household records with source attribution · Generated extraction is uncertain and active cooking sessions need stable instructions · Rejected silently treating extracted text as final or overwriting a recipe in place.
- 2026-08-30 · Model grocery ordering through a provider-neutral handoff boundary · Swiggy API/partner availability has not been verified and the core product should remain useful without it · Rejected coupling the initial architecture directly to Swiggy checkout.
- 2026-08-30 · Make the househelp experience audio-first, with spoken feedback for every activated control and automatic spoken guidance for each new ingredient or cooking step · Core users may not be able to read, so literacy cannot be a prerequisite for completing an assignment · Rejected treating text-to-speech as a later accessibility enhancement.
- 2026-08-30 · Put spoken-language selection in assisted setup and keep an easy language switch on every househelp screen · Language must be discoverable and recoverable without navigating text-heavy settings · Rejected a one-time global language choice hidden in settings.
- 2026-08-30 · Pair audio-first househelp guidance with one verified focal visual per screen: ingredient photo, consistent action icon, state cue, and optional step media · Purposeful visuals can reduce ambiguity for non-reading users, while visual clutter or unverified imagery can create new cooking errors · Rejected text-only screens, decorative graphics, and image-only instructions.
- 2026-08-30 · Treat YouTube video help as attributed, user-initiated playback through the official source/player · Platform policy and creator rights make downloaded or repackaged clips unsuitable as a default product behavior · Rejected automatically extracting and storing standalone YouTube step clips.
- 2026-08-30 · Approve Milestone 1 and the recommended starting defaults: responsive web app, public webpage import first, human review, English/Hindi pilot speech, homeowner-enrolled device with simple PIN, generated/cached speech with device fallback, curated verified visuals, meal slots, assigned-only househelp access, manual-entry fallback, and provider-neutral shopping before Swiggy · This is the smallest complete test of the homeowner-to-househelp loop · Rejected expanding the first build to YouTube extraction, direct grocery checkout, native apps, AI-generated cooking imagery, or human-recorded voice packs.
- 2026-08-30 · Authorize Milestone 1 implementation through the coordinator-managed isolated-worker workflow · The user explicitly requested the complete build with systematic documentation and verification · Rejected continuing planning-only or starting later milestones in parallel.
- 2026-08-30 · Use Node.js 24 with Next.js 16/React 19, TypeScript, Zod, SQLite/Drizzle for local persistence, Vitest, and Playwright as the Milestone 1 foundation · This provides a zero-key full-stack local build with typed contracts, deterministic data, and browser verification while keeping persistence/auth behind replaceable boundaries · Rejected separate frontend/backend scaffolds and committing to an unselected hosted database or identity provider.
- 2026-08-30 · Require reviewed English and Hindi guidance for the dish, every ingredient, every step, and any assignment note, then atomically pin both locale snapshots to the published recipe version · Language can change during cooking, so an assignment is only safe if either supported language preserves reviewed meaning without consulting mutable recipe data · Rejected validating only the initially selected locale or assembling cook guidance lazily after assignment.
- 2026-08-30 · Persist househelp progress server-side with assignment-scoped idempotency plus a bounded local retry queue and stale-response guards · Kitchen connectivity is intermittent and repeated taps are likely, but failures must never unlock cross-assignment writes or silently lose progress · Rejected client-only progress, treating every `409` as success, and allowing an indefinitely pending request to lock controls.
- 2026-08-30 · Keep Milestone 1 local and deployment-neutral after acceptance · Production identity, datastore, hosting, real-device voice behavior, and assistive-technology behavior are not yet validated · Rejected pushing or presenting the local demo session and SQLite choices as production-ready infrastructure.
- 2026-08-30 · Approve Milestone 2 as broad-source recipe import using native safe fetch and deterministic Schema.org extraction first, Firecrawl as a server-side fallback, and OpenAI structured extraction for incomplete pages and available YouTube transcripts · This extends source coverage while preserving the existing human-review boundary, evidence, and safe failure behavior · Rejected assuming one scraper handles every site or treating model output as authoritative recipe content.
- 2026-08-30 · Do not require a YouTube Data API key for the approved transcript path · Firecrawl can return transcript text for some public YouTube pages, while recipe import does not need channel-management or quota-bearing Data API features · Rejected adding an unrelated credential without a demonstrated product need.
- 2026-08-30 · Do not integrate Pick-a-Recipe, `yt-dlp`, browser cookies, or downloaded YouTube audio/video into the core importer · The inspected repository has no discoverable repository license and its download/transcription path creates licensing, platform-policy, operational, and evidence-quality risks · Rejected copying its code or using its local-download pipeline; an authorized-upload transcription spike may be considered separately later.
- 2026-08-30 · Extend the existing persisted import lifecycle before adding a separate background queue · The current draft/status workflow already provides a durable review boundary, and queue infrastructure is not justified until measured provider latency or deployment limits require it · Rejected adding speculative asynchronous infrastructure in the first broad-source slice.
- 2026-08-30 · Keep Firecrawl caching disabled and make Zero Data Retention an explicit opt-in capability · Live verification showed the standard paid account accepts `storeInCache:false` but rejects `zeroDataRetention:true` with `403`; the importer handles public sources only and documents standard provider retention · Rejected making all imports fail on ordinary paid plans or silently retrying a rejected ZDR request without the flag.
- 2026-08-30 · Bound OpenAI evidence extraction at 60 seconds while retaining the synchronous persisted import lifecycle for this slice · A live captioned recipe video completed successfully in roughly 42–52 seconds and timed out under the original 30-second bound · Rejected pretending the shorter timeout was production-ready or adding an unapproved background queue before deployment limits are selected.
- 2026-08-30 · Let househelp browse and choose among active assigned dishes, then return to that menu after completion · This removes the terminal completion dead end while preserving pinned recipe versions, servings, notes, homeowner visibility, and assigned-only authorization · Rejected exposing the homeowner's full recipe library or starting an unassigned recipe directly.
- 2026-08-30 · Keep `Cooking menu` as an explicit escape and make cooking-step review local-only · Navigation must remain available when speech or sync stalls, while reviewing an earlier instruction must not send duplicate or backward server progress · Rejected making menu return depend solely on a speech callback or persisting backward step movement.
